# 会议录音笔「小pan」暂不实现（封存设计）

**Status**: deferred — 2026-11-09 封存，仅当文末「重启触发条件」出现时才重新评估。

目的原本是：开会时只讨论流程图上的待确认项，会中自动记录谁说了什么、说了哪条待确认项的方案，散会时人逐条确认，省掉会后补笔记。设计已经收敛到可实施的程度，但**效果层的瓶颈是拾音硬件而不是认人**，且效果本身没有任何实测数据，因此不做。定制化功能、不是产品，不值得我们为它引入第一个后端依赖和逐次确认的人力成本。

## 为什么停（四层，别只看第一层）

**硬约束：单麦远场拾音**

3-5 人围一台笔记本，声音要经过房间衰减、反射、抢话才进麦。受影响的不只是"谁在说"，还包括**转录本身**：漏字、串句、重叠段落被合并。这不是模型问题，是拾音问题；换会议宝 / 麦克风阵列可解，但那就不是"打开 Mermaid Studio 点一下录音"了。

**可以绕过、但要付代价**

- **认人不给姓名（云端）**：通义听悟 FAQ 明确只做说话人分离，不给身份，只能会后改发音人名称。但这不等于没有解法：开源的 CAM++ / WeSpeaker / sherpa-onnx 都提供声纹注册与比对，3-5 人小样本注册是标准用法。所以认人是四层里**最容易绕过**的一条——要么会后手动绑名 30 秒/场，要么本地声纹，取决于远场准确率。
- **后端**：本仓库纯静态前端，API key 不能进浏览器，要加一个本地转发；音频还要上传第三方。
- **语音指令**：自由讨论里捕捉"小pan 帮我新增一条"，会误触发 / 漏触发，必须配可见回执和撤销。

**未验证（决定成败，但没数据）**

- "这句是否跟第 3 条待确认项相关"是 LLM 判断，**漏挂率 / 错挂率没人评估过**；错挂的后果是人确认时读到不相关的原话。
- 专有名词（节点名、系统名、人名）不加热词表会被转错，并连带把相关性判断做错——"转得对不对"和"归得对不对"是同一件事的两面。
- 收益本身：散会后 3-5 分钟逐条确认 + 未挂图项要会后挂线，是否真的比手写笔记省时间，要连续几场真实会议才知道。

**所以准确的说法是**：流程、界面、数据落点都已经想清楚，**效果层全部未验证**；效果层的瓶颈首先是拾音硬件，其次才是认人。

## 一个 1 小时的验证实验（重启前先做，不用写代码）

1. 用 MacBook 放在平时开会的位置，录一段真实的 3-5 人会议（手机也行，位置要一样）；
2. 音频丢给通义听悟，免费额度就够；
3. 只看三件事：**字错率、换人时说话人切分是否稳定、专有名词错多少**。

结论只有两种：可做但打折（认人靠手动绑名），或确实不行（等硬件）。这一步比再讨论十轮有用。

## 已经定下的部分（重启时不用重新推演）

- **小pan 只做三件事**：判断发言是否与某个待确认项相关；听到指令后新增一条；留一份原始文档。不做总结、不排议程、不提醒、不投屏、不播报说话人。
- **入口**：工具栏一个「声音」按钮 = 开始/结束录音，采 MacBook 自带麦克风。
- **界面**：右侧栏与检查器并列新增「确认项」面板；确认后画布上对应的虚线边变成实线（`dashedQuestions` 只认虚线，变实线后该行自动从导出的存疑清单消失）。
- **结论不进边标签**：仓库的边标签有「类型」或「类型: 说明」的固定规范，自然语言结论写进会议记录，不写进标签。
- **两遍采集**：会中只做粗打点，散会后用整场转录重跑一遍；实时结果不作为最终依据。
- **三态**：已形成结论候选 / 讨论了但没结论 / 完全没提；只有第一类进入确认流程，其余保持虚线。
- **口述新增**：指令"小pan 帮我新增一条"→ 先落为**未挂图项**（只在面板里，导出时附在存疑清单末尾 `- [ ] 说明（未挂图）`），散会后由人指定起点/终点才画线。理由：会上没人说清它连哪两个节点，硬猜等于让 AI 替人画流程。
- **指令要有回执**：命中时弹 3 秒「已新增：…（可撤销）」，否则是无声失败。
- **确认交互**：面板逐条 `[合适 → 变实线] [不合适 → 保持虚线并标注"本次未通过"] [跳过]`，并提供键盘 J/K/Enter 的"过一遍"模式。
- **原始文档**：带时间戳 + 说话人姓名的逐字稿 Markdown，绑定这次会议 / 这张图；不随 `.md` 导出；音频默认转完即删、可按次开启保留。
- **一次录音锁一张图**：录音中切图 → 提示先结束录音。
- **聚焦不归小pan**：靠会前发流程图和虚线，小pan 不做任何干扰。

## 考虑过但否掉的方案

- **投屏 + 大屏 + 逐条集体过**：被否，现场没有大屏，且"集体确认"在这个团队就是"大家坐在一起开会"，没有第二个环节。
- **AI 起草候选结论**：会把 3 件事变成 4 件，且是第二层失真；确认要以原话为证据。
- **自动认人 / 全本地推理**：没有否掉，只是没先做——见下面的开源调研和验证实验。

## 开源方案调研（2026-11）

先排掉一个方向误导：**Typeless 是语音听写键盘，不是会议记录工具**——按热键说一句，按当前 App 语境润色后写进光标处，官方未公开架构。它的开源对照物 [OpenTypeless](https://github.com/tover0314-w/opentypeless)（MIT）把流程做成"Rust 采集 → STT 供应商（BYOK）→ LLM 润色 → 键盘输出"，没有多人、没有说话人分离、没有长会议。照它的架构做小pan 会做偏。

真正对得上需求的是这些：

| 项目 | 定位 | 用在哪 |
| --- | --- | --- |
| [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/) | 端侧 VAD + ASR + 说话人分离 + **声纹注册识别** | 正好对应"提前登记音色、会上自动认人" |
| FunASR + CAM++ | 中文 ASR + 声纹比对 | 中文会议转写主力 |
| WhisperX / faster-whisper / pyannote | whisper + 分离 + 时间对齐 | 多语言备选 |
| [Meetily](https://github.com/Zackriya-Solutions/meetily)（MIT） | 本地会议助手：Tauri + Rust + Next.js，本地 Whisper/Parakeet + Ollama 纪要 | 采集 / 实时转写 / 本地存储的参考实现 |
| Tingji / meet-transcribe | FunASR + LLM 的本地会议转写 | 中文场景最短路径 |

**一条值得注意的信号**：Meetily 开源版（MIT）做了本地转写和纪要，但"说话人识别（谁在说）"被放在 PRO 付费版（$10/人/月）。说明这块不是没人做，而是难做且能卖钱。

**结论**：开源把隐私、费用、后端三条顾虑基本消掉——全本地闭环可行（sherpa-onnx + FunASR/CAM++，零费用、零上传）；代价是"加一个本地推理服务"（模型 1–2GB + onnxruntime），比云端那套"小转发"重。**唯一没变的是拾音。** 许可证要逐个核对：pyannote 模型需在 HF 申请，FunASR 部分权重有独立条款。

## 重启触发条件（满足任一条再回来）

1. 上面那个 1 小时实验显示**单麦转录质量可接受**（字错率可忍、换人切分稳定）——那就直接用"会后手动绑名"的方案开工，不需要等声纹；
2. 云端 ASR 提供**声纹注册 + 姓名识别**，且价格 ≤ 1 元/小时；
3. 或本地 FunASR / sherpa-onnx + CAM++ 声纹在实测里准到可用（可全本地闭环，零费用零上传）；
4. 或团队换用会议宝 / 麦克风阵列等能给出清晰分离音的硬件；
5. 或场景变形为"不开会也要把讨论整理成待确认项"——那是另一个形状，本文的很多结论（未挂图项、两遍采集）仍然适用。
